Editing a result in place

The opportunity tab of the mockup above is live: switch to it, turn Edit mode on, change a cell or mass-set a field, then press Save changes to walk the whole preview / production-confirmation / Update result sequence.

A result grid can be corrected and written back to the org without leaving the tab. Turn on the Edit mode toggle in the filter row: the editable columns become writable, every other column is dimmed, and a bar appears with the mass-set controls, Save changes and Discard.

Editing is only offered when the result can be written back safely. When the toggle is greyed out, hover it — its tooltip names the reason:

Tooltip on the disabled toggleWhy
Add Id to your SELECT to enable editing an update addresses records by Id; without it there is nothing to write to
Editing is Partner-only (uncheck Tooling API) Tooling results are not writable this way — uncheck Tooling and run again
Editing is not available for Bulk results the Bulk path returns rows without the describe the editor needs
FROM object unknown the column types come from the describe of the FROM object

Only direct, updateable, non-formula fields become editable — a relationship path such as Owner.Name, the Id itself and any formula or read-only field stay dimmed. A cell you change is highlighted pending; a value the describe rejects turns invalid with a tooltip and blocks the Save. The check is local, before any call to the org: type, restricted picklist, length, required field emptied. A counter next to the buttons shows how many changes are pending and surfaces the first error in full.

Emptying a cell clears the field in Salesforce: it is sent as a null (fieldsToNull), not as an empty string.

Mass-set — many rows at once

In the edit bar: Set [field] = [value], then Apply. The value control adapts to the field — a picklist offers its own values instead of a free-text box. Tick selection only to restrict the change to the rows you selected; otherwise it applies to every displayed row.

Displayed is the operative word. When the result holds more rows than the grid shows, Apply warns first — « N row(s) of the result are not displayed and will NOT be modified. Continue ? » — so a mass-set never touches what you cannot see. And Apply only stages the change: nothing reaches the org until Save changes.

Saving

  • A preview lists every pending change, Id by Id, as field: old → new, with the record and field counts, the object and the org.
  • On a production org a second, explicit confirmation is required — it names the org. It does not appear on a sandbox.
  • The write runs off the UI thread; Save, Discard, Apply and the toggle stay disabled while it runs.
  • An Update result column then reports row by row: rows that succeeded leave the pending set and their new value becomes the baseline, rows that failed stay red with the org's own error message — a partial failure is never silent.
  • Under the hood the write is a Partner API update(List<SObject>), chunked by 200 records.

SOQL Executor — Key Features

  • Multi-tab query editor with monospace dark theme
  • SELECT * expansion with configurable priority fields per object
  • Tooling API mode for metadata queries (ApexClass, CustomObject, etc.)
  • Fast count (COUNT_DISTINCT) without fetching all rows
  • Bulk API v2 mode for large datasets (> 10 000 rows)
  • Relation field resolution (e.g. RecordType.Name, Owner.Name)
  • Row filter on result table (client-side search)
  • CSV export with configurable column separator
  • Saved query library with open-folder shortcut
  • Per-tab timeout and max-rows override
  • Edit mode — correct a result grid in place and write it back through the Partner API (needs Id in the SELECT; Partner only, non-Bulk)
  • Mass-set one field across the displayed rows, warned when the result holds rows the grid does not show
  • Local validation before Save (type, restricted picklist, length, required), Id-by-Id preview, an extra confirmation on production, and a per-row Update result column
